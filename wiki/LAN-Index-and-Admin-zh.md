# 内网索引与管理页

[English](LAN-Index-and-Admin) | **简体中文**

webvpn 可以再开一个只能从内网访问的监听器。它只提供两样东西，别的什么都不做：

- `GET /` —— 免登录的卡片列表，直接链到各服务的内网地址。
- `/admin` —— 需要登录的管理页，用来管服务、用户和权限。

它够不到反向代理，也够不到任何后端。这个监听器上没有任何转发流量的路由。

## 为什么要有它

人在屋里访问服务，不该先出内网、绕一圈 Cloudflare 再回来登录。内网索引只要点一下。管理页则是为了让你加服务、授权时不用改 YAML、跑 `-check`、修文件属主再重启。

## 配置

```yaml
lan_index:
  listen: "192.168.1.50:80"
  host: "192.168.1.50"
```

| 键 | 含义 |
|---|---|
| `listen` | 要绑定的 `host:port`。留空即关闭。 |
| `host` | 用来替换链接里回环目标的主机名。有服务指向 `127.0.0.1` 或 `::1` 时必填。 |

绑**内网地址，别写 `0.0.0.0`**。在有公网地址的机器上，`0.0.0.0` 等于把你在跑什么公开给全网。代码会拒绝内核给出的非私有来源地址，但那只是兜底；真正的控制项是绑定地址。

1024 以下端口需要 systemd 单元给 `CAP_NET_BIND_SERVICE`，见 [部署](Deployment-zh#systemd)。

### 回环目标

另一台机器上的浏览器会把 `127.0.0.1` 解析成**它自己**，所以指向 `http://127.0.0.1:3000` 的卡片是死链。设置 `lan_index.host` 会替换主机名、保留协议和端口。如果有服务指向回环但 `host` 为空，启动直接报错，而不是给你一页死链。

单个服务可以用 `lan_url` 覆盖生成的链接：

```yaml
  - name: "Grafana"
    subdomain: "grafana-vpn"
    target: "http://127.0.0.1:3000"
    lan_url: "http://192.168.1.50:3000/"
```

## 这个监听器的安全模型

- 它有自己的 mux，其他路径一律 404。
- 它不信任 `CF-Connecting-IP` 或 `X-Forwarded-For`；内网任何客户端都能伪造这些头。日志用内核给的 `RemoteAddr`，非私有来源直接拒绝。
- 管理页会话用**派生密钥** `HMAC(sessionKey, "webvpn-lan-admin")` 和自己的 Cookie，和门户会话互不通用。这是构造上成立的，不是某处 `if` 判断。
- 管理页 Cookie 不写 `Domain`，也不是 `Secure`（内网监听是明文 HTTP）。它只属于你打开管理页时用的那个主机名。

**这个监听器是明文 HTTP。** 管理页会话 Cookie 在内网里明文传输，同网段能抓包的人就能拿到。这是"管理页不上公网"的固有代价。不接受的话，只能给这个端口套 TLS，或者把管理挪到隧道侧——后者就不满足"仅内网"了。

## 使用管理页

打开 `http://<内网IP>/admin`。只有 `admin: true` 的账号能登录；普通账号即使密码正确，也会在登录表单被 401 拒绝。

可以：

- 增删改服务；
- 增删用户；
- 改密码；
- 勾选每个用户能访问哪些服务。

改动立即生效，原子写入 `state.json`。

### 自举：第一个管理员

没有管理员的状态在界面上无法改回来，所以：

- 配置里没有任何 `admin: true` 时，启动会把第一个用户提升为管理员并打 `WARN`。
- store 拒绝持久化没有管理员的状态，界面也不会让你删掉或降级最后一个管理员。

首次启动后，去管理页确认管理员是你要的账号。

### 播种是"全部授权"

`state.json` 第一次生成时，每个用户都会拿到全部服务。这是为了保持加 ACL 之前的行为，避免升级后有人突然用不了。收紧权限在管理页里做。`config.yaml` 里写的 `services:` 名单在播种时被忽略。

## 访问控制语义

- **默认拒绝。** 用户的授权列表里有该服务的 subdomain，才能访问。
- **管理员隐含拥有全部。** 管理页上管理员的勾选框显示的是**存下来的名单**，不是实际权限。这一点很重要：如果界面给管理员显示全选、你一保存，就会在不知情的情况下写入一份全授权名单。
- **每个请求现查。** 会话 token 只带用户名，不带权限集合。收回授权或删账号，下一次请求就生效——手里合法的 Cookie 救不了他。
- **删用户不吊销 Cookie，但不需要。** 授权每次都重新读，未知用户什么都拿不到。
- **ACL 只覆盖隧道。** 后端在内网本来就直连可达，同网段的人可以绕过索引。语义是"公网经隧道这条路对你设防"，不是"你看不到这个服务"。这也是内网索引照旧列全部的原因。

## 常见坑

| 症状 | 原因 |
|---|---|
| 启动报 `bind: permission denied` | 1024 以下端口，单元没给 capability。`NoNewPrivileges=true` 下 `setcap` 会被静默忽略。 |
| 启动报 `lan_index.host is required` | 有服务指向回环。设 `lan_index.host` 或该服务的 `lan_url`。 |
| 卡片指向 `127.0.0.1`，别的机器打不开 | 回环目标没配 `host`/`lan_url`。 |
| 登录管理页后下一步弹回登录 | 换了主机名（IP、域名、别名）。管理页 Cookie 是 host-only，每个主机是独立会话。 |
| 索引页能从公网打开 | `listen` 是 `0.0.0.0`；改成内网地址并重启。 |

## 局限

- 索引页按设计免登录。同网段任何人都能看到服务名和描述。里面没有凭据，也不能借此代理，但清单本身是公开的。
- 管理页等于整套 VPN 的钥匙。用强密码，别随手发 `admin: true`。
- ACL 不限制内网直连后端。网络分段是另一个问题。
